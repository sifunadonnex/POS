## Implemented

- Better Auth 1.7.4 email/password sessions with controlled staff accounts, required verification, recovery/password change, authenticator MFA and recovery codes.
- Server-side manager/cashier authorization, manager staff administration, suspension/session revocation, security audit and 15-minute inactivity locking. Public signup and direct role/profile mutation are blocked.
- Transactional sale, return, purchase, shift and stocktake writes enforce the same conditional MFA policy as the identity boundary: managers and any 2FA-enabled cashier require a verified MFA session, while a verified password-only cashier remains authorized for cashier work.
- Durable encrypted SMTP outbox and retry worker are implemented; SMTP acceptance/inbox delivery and hosted scheduling remain unverified.
- Catalogue categories/products with `each`, `pack`, `kg` and `l` sale units. Prices are exact integer minor units; `kg`/`l` later use 0.001 quantity steps while `each`/`pack` use whole quantities.
- Unique SKU/barcodes, archive/reactivate, immutable unit after creation, optimistic revisions, append-only product/category history, manager reason capture and idempotent request receipts.
- UTF-8 CSV preview/import with bounded size/rows, create-only semantics, conflict checks and one-transaction all-or-nothing import.
- Responsive shadcn/Base UI screens for identity, staff security and catalogue workflows. Authentication now uses an image-backed retail entry shell with a focused staff sign-in panel, guided recovery/email-verification states, staged MFA enrollment/challenge UI, accessible password visibility controls and explicit loading/offline/locked states. The project-local background was generated without logos, text or identifiable people.
- Product UI direction is now aligned to a clean Dynamics 365 Commerce-inspired operational shell, using shadcn components and a dense commercial dashboard layout rather than a consumer SaaS aesthetic. The authenticated workspace now occupies the full viewport instead of sitting inside a sign-in card, keeps the active staff/session control in the sidebar, hides the redundant register shortcut while the register is open, and updates the browser title for the active module. A Pay & Go favicon/theme colour, shared `KES`/Africa-Nairobi formatters and thin theme-aware scrollbars remove remaining starter-branding, locale and native-browser inconsistencies without hiding scroll affordance.
- The cPanel release now builds the Vite frontend locally, packages it under `public/` with the compiled Nest API, serves the staff portal from the same origin, keeps `index.html` uncached and applies immutable caching only to fingerprinted `/assets/` files. API routes remain under `/api`; an absent frontend build preserves API-only startup for diagnostics.
- Hosted authentication has a one-time initial-manager bootstrap that requires an empty user table, explicit manager/email-control confirmations and a private temporary input file. It hashes the password through Better Auth, marks only that initial manager verified, records the provisioning audit transactionally and refuses repeats. Public signup remains disabled; normal additional-staff onboarding still requires verified SMTP delivery.
- Dashboard now presents role-specific quick actions, a live operational workspace and accurate links to every implemented sales, returns, catalogue, stock, purchase, stocktake and reporting flow. The manager view loads the real daily summary with operational KPIs, payment-mix percentages, shift reconciliation, loading/error/retry states and product-specific low-stock attention, plus a prioritized current/threshold alert list and a server-backed seven-day sales/refund pulse with net sales, completed sales and average basket. The cashier view keeps manager figures private and does not request sales insights.
- Staff workspace sidebar is grouped into Workspace, Sell, Inventory, Insights and Administration, with implemented modules active and unavailable work kept out of the operator path rather than exposed as fake actions.
- A first offline edge boundary is implemented behind `PAYGO_RUNTIME_MODE=edge`: the API binds to loopback, requires a stable store UUID, uses local PostgreSQL as the single checkout authority and refuses Daraja. Completed cash checkout writes a versioned `cash_sale.completed` outbox event in the same transaction as the sale/payment/stock/cash ledger. An authenticated status API and workspace badge distinguish Hosted from Local and expose the queue/delivery count. Internet-loss events now recheck the same-origin API, allowing a reachable local service to retain the session. See [the edge setup note](OFFLINE_EDGE_SETUP.md).
- Store delivery is disabled by default and uses a separately configured per-store secret. The edge worker claims five events at a time, signs the canonical envelope and timestamp, requires HTTPS, retries failures with bounded exponential backoff and marks delivery only after an exact accepted/duplicate acknowledgement. New schema-version-2 events include immutable cashier/product display snapshots; the hosted parser retains version-1 compatibility with explicit legacy labels so an older queued event is not stranded. The public hosted boundary bypasses staff-session auth but verifies store ID, a five-minute timestamp window and a constant-time HMAC before accepting input. It validates cash-sale totals and identities, then transactionally deduplicates the event and aggregate identity into `sync_inbox` and inserts append-only sale/line reporting projections before acknowledging. These read-model rows do not mutate hosted operational sales, payments or stock. Status exposes received/projected gaps, the workspace warns on a gap, and a manager-only endpoint reconciles exact event counts and minor-unit totals.
- The bootstrap guard/checkpoint slice adds one durable store state row with immutable store identity, checkout authority, generation and configuration version/digest. Internal transitions reject out-of-order/replayed checkpoints, stale generation fences and cutover with open shifts or unresolved attempts. After a cutover, PostgreSQL triggers block hosted operational sale/stock writes and the API returns a conflict before running the handler. Edge staff/catalogue mutation routes return forbidden; reads remain available. The initial snapshot and later change batches require manual private-file transfer. There is no activation endpoint or generation check on sync delivery yet, and no active cutover.
- The ordered configuration slice journals every hosted roster/category/product/barcode change after first snapshot publication in the source transaction, including CSV import and email verification/suspension. A store-row lock assigns committed contiguous versions. An MFA-proven hosted manager exports a bounded, signed 15-minute change batch from the edge cursor; the edge CLI validates store/generation/signature/digest/revisions and applies the batch atomically with an append-only source audit and cursor. A local checkpoint CLI retrieves the cursor even when expired roster policy blocks browser login. Empty signed batches refresh the roster check. Applied staff changes revoke local sessions. Edge checkout and authentication deny missing, future or 24-hour-old roster checks. This is a manual private-file transport for the single-PC phase, not automatic sync or cutover.
- Sales register now uses active catalogue lookup/barcode search, server-authoritative basket quotes, and a single request-replay-safe cash checkout transaction. A cash checkout commits the sale, payment, tender, stock reduction and cash movements together; it calculates change before confirmation and includes cash received/change given on the retrievable receipt. Held orders are server-authoritative with ownership, optional notes, cashier/manager scoping and replay-safe optimistic `held` to `resumed`/`cancelled` transitions; resume refreshes current catalogue data and re-quotes without reserving stock or prices while held. A `GET /api/shifts/current` read lets register refreshes recover the active shift instead of opening a duplicate.
- Paid-sale receipts now render as a compact supermarket-style 80 mm paper preview with immutable item/SKU snapshots, unit-aware quantity and price lines, total, payment, cash tender/change, Nairobi timestamp and sale reference. Print media isolates the receipt from the application shell so the browser no longer prints the register, navigation or basket. Simulated output is visibly marked `TEST — NOT A TAX INVOICE`; the selected printer driver still controls the physical roll length.
- Sales history is now a responsive server-backed workspace for managers and cashiers. It provides a paged seven-day ledger by default, reference/cashier search, a bounded date range, paid/part-paid/unpaid and refund indicators, and line/payment drill-down. Managers can inspect all completed sales; cashier queries and detail reads are server-scoped to their own sales.
- Confirmed payments attach to the active shift. Tendered cash records append-only `cash_in` and, where needed, `cash_out` change movements, so shift closing derives expected cash from the movement ledger. Card and M-Pesa availability comes from an authenticated backend capability read. Card remains unavailable; M-Pesa is reported available only when the complete Daraja server configuration is enabled.
- Card/M-Pesa have a provider-neutral durable attempt foundation and a capability-aware register flow: request replay protection, exact outstanding-balance capture, originating-shift linkage, pending/confirmed/failed/unknown states, append-only provider events, duplicate-event protection and explicit reconciliation. The register finalizes the sale before starting an external attempt, shows a receipt only after confirmation, freezes basket and shift-closing actions while the result needs resolution, and retains the recovery checkpoint across refreshes once the finalized sale is known. Failed attempts retry the same sale with a new request ID; pending/unknown or unconfirmed starts reuse/reconcile the existing attempt instead of creating another sale.
- Safaricom Daraja M-Pesa Express is integrated behind `DARAJA_ENABLED=false`: server-side OAuth token caching, STK Push initiation, phone normalization, sandbox/production endpoint selection, public token-protected callback handling and status-query reconciliation. The register captures the customer's Kenyan mobile number and blocks non-whole-KES M-Pesa totals. A callback confirms payment only when the checkout reference, receipt and exact amount are present and match the stored attempt; duplicate callbacks are idempotent. A successful status query without returned amount remains unknown. No credentials were added and no external provider request was made. See [Daraja setup](MPESA_DARAJA_SETUP.md).
- Backend stock API for opening, receiving and adjustments with append-only inventory movements and quantity validation for each/pack/kg/l units. Stock balance and movement-history reads normalize PostgreSQL `bigint` values to the numeric browser API contract; history also exposes sale and customer-return movements.
- Manager Stock control workspace now loads real stock balances, supports search and paging, posts opening/receive/adjust movements with exact unit-aware quantities and replay-safe request IDs, and displays per-product movement history with loading, empty, error and retry states. Product rows and the selected-product panel show the configured threshold and recompute low-stock status immediately after a confirmed movement. Managers configure an optional threshold in Catalogue using whole quantities for `each`/`pack` and 0.001 steps for `kg`/`l`; catalogue history retains every threshold change.
- Manager Purchase intake workspace now lists and creates suppliers through manager-only endpoints, searches active catalogue products, builds exact unit-aware receipt lines, previews totals, and posts supplier receipts through the existing transactional purchase endpoint with replay-safe retry handling. It is wired into the manager-only Inventory sidebar.
- Manager Purchase reports workspace now filters a date-bounded reconciliation report, shows received/returned/net purchase totals, rolls activity up by supplier, reconciles each receipt against supplier returns, and drills into a signed supplier ledger. The reads are manager-only and derive from append-only receipt/return records; no browser cache is used for authoritative history.
- Manager Reports now opens a sales-insights view by default and keeps Purchase reconciliation as a neighbouring report. Sales insights supports an inclusive date range of up to 93 days and shows net sales, average basket, refunds, active cashiers, a Nairobi-day sales/refund graph, confirmed payment mix, cashier performance and top products. On a synchronized hosted runtime it offers explicit All sources, Hosted operations and configured edge-store filters; cashier/product rows retain source labels and a live indicator compares received versus projected events. Hosted operational and synchronized read-model tables remain separate. Because edge returns are not replicated yet, any source including edge sales displays a coverage warning instead of implying that refund/net figures are complete. The shared timeline compresses all selected days into the available card width instead of requiring horizontal chart scrolling, keeps the first/middle/last dates visible and exposes exact daily values to assistive technology. The API is manager-only, fills days without sales and uses integer-minor-unit values. Gross product ranking intentionally does not claim profit or margin while supplier-cost allocation remains undecided.
- Purchase-report screen coverage verifies the rendered reconciliation totals, receipt table, valid and inverted date ranges, and supplier-ledger drill-down in addition to the existing API, service and PostgreSQL business-flow tests.
- Returns workspace now searches completed sales, loads server-calculated refundable line quantities, previews the same cumulative half-up refund allocation used by the server, and submits replay-safe customer returns that restore stock and record the paid refund through the existing transactional return endpoint. It is available to cashiers and managers in the Sell sidebar.
- Manager Stocktake workspace now loads authoritative stock balances, supports search and paging, accepts exact unit-aware physical counts, previews the reconciliation delta, and posts replay-safe counts through the transactional stocktake endpoint. It is wired into the manager-only Inventory sidebar.
- Supplier purchase receipt and supplier-return flows with request replay protection, supplier validation, exact unit-aware totals, cumulative return limits, stock movement logging and append-only receipt history. Supplier directory listing and manager creation are now available.
- Sales, customer returns, shifts, reports and stocktake flows are transactional and replay-safe. Checkout and refunds use server-authoritative catalogue/sale prices; split payments and repeated returns cannot exceed their source totals.
- Stock-changing product reads now lock only the catalogue row in PostgreSQL. This preserves per-product serialization without trying to lock the nullable inventory side of a left join, which previously prevented first receipts and sales from committing.
- Forward migrations through `202610020003_sync_reporting_projection` permit `stocktake` inventory movements, enforce non-negative stock, permit only one open shift per cashier, allow a single open-to-closed shift transition, link confirmed payments to shift reconciliation, retain cash tender amounts, persist protected external payment attempts/events, add durable suspended-order history and low-stock thresholds, and add the edge outbox, hosted inbox/delivery schedule and append-only synchronized cash-sale reporting read model.
- Fractional checkout lines now round to the nearest minor unit with exact halves up after exact integer multiplication. Repeated partial customer refunds use the difference between rounded cumulative values, so a full return reconciles exactly to the immutable sale-line total without over-refunding. Supplier receipt/return lines remain exact-only pending a supplier-cost rounding decision.
